## 补充 beginner 教程第 5 章：加速度计读数公式的推导

用户反馈「accel[0] = -g·sin(pitch) 这些我都不知道啊」——说明教程第 4-5 章
只给了结论没给推导，是漏项。

### 补了什么
- 新增 5.1「先把读数算出来」：两步推导法，只用直角三角形
  1. 只做 pitch：读数箭头与机体 z 轴夹角 p，分解出 g·cos(p) 和 -g·sin(p)
  2. 再加 roll：**绕哪根轴转，就不改变那根轴上的分量**，所以 accel[0] 不变；
     y-z 平面里长度 g·cos(p) 的向量再按 roll 分解
- 新增 5.2 roll 推导：accel[1]/accel[2] = tan(roll)，cos(pitch) 约掉
- 新增 5.3 pitch 推导：邻边必须用 sqrt(ay²+az²)，不能直接用 az
  数值证据：pitch=30/roll=45 时，sqrt 版 30.000°，az 版 39.232°（错 9°）
- 新增自检技巧：√(ax²+ay²+az²) 应恒等于 9.8，可用于现场判断传感器/单位
- 新增 ±90° 限制说明（sqrt 只返回正值，120° 会折成 60°）

### 教学要点（后续复用）
- 推导"某姿态下的传感器读数"时，用「分步旋转 + 直角三角形」讲，比旋转矩阵易懂得多
- 关键直觉句：「绕某根轴旋转不改变该轴上的分量」——这句话解释了 roll 为什么
  不影响 accel[0]，也解释了为什么 sqrt(ay²+az²) 与 roll 无关

## 补充教程第 10、11 章：四元数乘法与 q·v·q⁻¹ 的推导

- 10.2 16 项展开表（4×4），按列归并 → 得到代码那四行

- 11.4 手算 90° 转 (1,0,0) → (0,1,0) 全过程

## 修 yaw 精度问题 + 零位标定数据突变 + 接上 EmberProbe

### 日志分析结论（重要，别重复推）
- 采样约 400 Hz（2.45 ms），跨度 16 h
- 检测出 68 个静止平台。正向"转90°"实测 +85.4 / +86.9 / +91.4（均值 87.9）

  标定未完成时输出的是"原始角度-0"，标定完成那一刻跳到 0
- 关键推论：**纯灵敏度误差在往返时会抵消**（+90k-90k=0），

### 关键区分（已经反复绕圈，必须讲清楚）
- **bias 0.1 °/s 是传感器自己的零偏，不是漂移**

### 用户问 RM 里 yaw 怎么用
标准做法：**控制误差永远先 wrap 到 ±180**，和存的是 ±180 还是 ±360 无关。
```c
float wrap180(float a){ while(a>180)a-=360; while(a<-180)a+=360; return a; }
err = wrap180(target - current);
```
- 底盘跟随 / 云台瞄准：用 wrap180 后的误差（最短路径）
- 小陀螺：控的是角速度 `g_yaw_rate_deg_s`，或者用 `g_att_yaw_total_deg` 数圈
- 绝对航向：6D 给不了，要磁力计或视觉

## 用户问"不是误差 2 度吗" —— 拆解正反向误差


### 为什么可以断定这 2~3.5° 不是传感器的
- **若是零偏误差 δ**：正向 −δT、反向 +δT，互相抵消（和观测一致）。
  反推 δ = 3.51/23 s = 0.153 °/s，反向 2.59/19 s = 0.136 °/s，两个居然很接近。
  **但**：δ=0.14 °/s 的话，后面静止 96 秒会漂 13°；实测只有 0.006 °/min。**矛盾，排除。**
- **若是尺度误差**：正反向误差应该**同号**（都和转过的角度成正比），
  往返会累加而不是抵消。实测是抵消的。**排除。**
- ⇒ 只能是**实际转角本身不等于 1440**。手转 4 圈做不到 4.000 圈。

### 真正能测的只有往返残差
8 圈（2880°）净残差 −0.92° = **0.032%**，两次独立测试一致（3 圈 0.027%）。

单方向的 2~3° 无法和"你到底转了多少"分离，没有绝对参考就测不出来。
要单方向准，只能闭环：记下目标 total，转到 |target − total| < 0.5° 就停。

## 波形优化 + 清理 + 重写教程

### 波形优化（截图里 yaw 有 ±0.03°、约 5 秒周期的慢晃）
原因不是白噪声（白噪声是快抖），是**低频成分**。
`yaw = ∫(gyro - bias)dt`，bias 是 gyro 的低通 → 积分后 yaw 的低频成分 ≈ tau × gyro 的低频成分。
**所以 tau 越小，慢晃越小。**
`ATT_REST_BIAS_TAU` 1.0 → **0.4**，低频增益降到 0.4 倍。
安全性：ZARU 前面还有 0.5°/s 的闸，>0.5°/s 的转动不会被吃。

## CAN + C620 从 F4 移植到 H7（用户：教我怎么移植）

### 核心认知：不是同一个外设
F4 = bxCAN，H7 = **只有 FDCAN**（Drivers 里只有 stm32h7xx_hal_fdcan.c）。
两套完全不同的硬件模型，代码不能复制。

### H7 工程本来就有 FDCAN1（用户已完成一半）
ioc 里已配好：PD0=RX/PD1=TX(AF9)、1 Mbps、FDCAN_FRAME_CLASSIC、
StdFiltersNbr=1、RxFifo0ElmtsNbr=16、NVIC FDCAN1_IT0/IT1 优先级 5。
但 **it.c 里没有 FDCAN1_IT0_IRQHandler**（CubeMX 没生成），fdcan.c 里
**TxFifoQueueElmtsNbr=0**（发不出去）。

### 波特率算法
- F4：APB1 42MHz / (7 × (1+4+1)) = 1 Mbps
- H7：FDCAN clk = HSE24M/PLLM2×PLLN40/PLLQ4 = **120 MHz**，
  120M / (3 × (1+29+10)) = 1 Mbps
- 注意 F4 的 BS1/BS2 是枚举值，H7 的 TimeSeg1/2 是**真实 TQ 数**

### 过滤器模型差异（最大的坑）
- bxCAN：28 bank，CAN1 用 0~13，CAN2 用 14~27，支持 **IDLIST**（32位可塞2个ID）
- FDCAN：**没有 IDLIST**。StdFiltersNbr 个独立元素，每个是 (ID1, ID2)，
  由 FilterType 决定含义：MASK(ID+掩码) / RANGE(起止) / DUAL(两个ID)
- 上限 128（标准），Message RAM 共 2560 words
- 本工程取 **StdFiltersNbr=16**（8 个 C620 + 8 余量）
- 标准/扩展元素**各自从 0 编号**，扫描空闲索引时必须连 ide 一起比

### 三个必踩的坑（都写进教程了）
1. `TxFifoQueueElmtsNbr=0` → 发送静默失败，能收不能发
2. `StdFiltersNbr=1` → 只能配 1 个元素，第 2 个电机注册就 assert 失败
3. **过滤器必须写在 HAL_FDCAN_Start 之前** → 启动后 ConfigFilter 静默无效
   （SIDFC.LSS 只能在 CCE=1/INIT 模式写，HAL 不会自动进 INIT）

## 修复 g_c620_send_fail 上电固定涨 50 次

用户报「都正常了也可以转但是为什么会有50失败」。定位：不是总线问题，是
**上电时陀螺标定忙等把 C620 任务饿死，恢复后 vTaskDelayUntil 补发突刺打满 TxFIFO**。

### 因果链
1. `BMI088_Calibrate_Gyro` 里 1000 帧 `BMI088_Read` 是纯忙等，全程不让 CPU，实测 ~50 ms
2. BMI088 任务优先级 54 > C620 任务 50 → 这 50 ms 里 C620 任务零次调度
3. 恢复后 `vTaskDelayUntil` 落后 50 个 tick，会**连续立即返回 50 次**硬补发
4. 每次调用 C620_SendAll → 前 8 帧填满 8 深 TxFIFO，第 9 次起
   `HAL_FDCAN_GetTxFifoFreeLevel()==0` → HAL_BUSY → 计失败
5. 50 - 8 ≈ 42，与用户看到的 50 数量级完全吻合

### 三处改动
- `modules/BMI088/bmi088.c`：标定内层循环每 32 帧 `vTaskDelay(1)`（新增 FreeRTOS.h/task.h 依赖）
  - 注意 `taskYIELD()` 无效：只让给同/更高优先级，C620 更低
  - 代价：多 31 ms，标定总时长 ~80 ms
- `APP/app_task/app_task.c` C620_Task：落后 >2 周期就把 `last_wake` 对齐到 now，跳过错过的周期
- `APP/app_task/app_task.c`：区分 HAL_ERROR（计 send_fail）与 HAL_BUSY（新增 g_c620_send_busy）
- `APP/app_debug.c/.h`：新增 `g_c620_send_busy`

### 教学要点（后续复用）
- 控制指令「最新一帧才有意义」，补发历史指令毫无价值 → vTaskDelayUntil 必须配落后对齐
- 判断 send_fail 性质：一次性定值 = 启动瞬态；持续快速增长 = 真总线故障（Bus-Off/无 ACK）
- 高优先级任务里的长忙等是 RTOS 头号陷阱，`taskYIELD` 不能解决优先级倒挂，必须真阻塞

### 方案调整（用户指正，采纳）

用户：「不用这样改吧你标定放在rtos任务启动前就行了」—— 完全正确，前面的三处补丁属于
治标，把标定挪到调度器启动前是治本。

**最终方案**：`BMI088_Calibrate_Gyro` 从 `BMI088_Task` 移到 `App_Init_Devices()`
（main.c:104，在 osKernelInitialize/osKernelStart 之前）。
- 标定期间没有任何任务存在 → 不存在优先级倒挂、不存在补发突刺
- `bmi088.c` 不必依赖 FreeRTOS（模块层保持解耦）
- `HAL_Delay(300)` 在此处安全：中断已开、SysTick 在跑，只是调度器未启动

## 电机安装方向改成可配置数组

用户：「g_c620[i] = C620_Init((uint8_t)(i + 1), &hfdcan1, false); 感觉有问题啊
有的要正转有的要反转怎么办不是那个x型吗」

### 改法
`app_init.c` 新增 `static const bool c620_reversed[APP_C620_MOTOR_NUM]`，
`C620_Init` 第三参数改成 `c620_reversed[i]`。逐个电机改数组即可，不动 c620.c。

### 概念边界（重要，以后别再混）
| 现象 | 归属 |
|---|---|
| 电机对称安装、输出轴朝向相反 → 同样电流两边转向相反 | 驱动层 `reversed` |
| 麦轮 X 型平移/自转时四轮转向不同 | 底盘运动学解算层 |

X 型前进时四轮同向；差异只出现在平移（左前+右后 vs 右前+左后）和自转。
把解算塞进 reversed 会导致以后双重取反。

### 已知隐患（待用户写速度环前处理）
`C620_SetCurrent` 里 `reversed` 只翻转**电流指令**，
`C620_RxHandler` 里的 `speed_rpm_out` / `angle_deg` 没有翻转。
纯电流（力矩）控制无影响；速度闭环会因为目标与反馈符号相反而发散。
修法：在 c620.c 的 RxHandler 里给 speed/angle 也乘 `reversed ? -1 : 1`。

## 让 reversed 同时翻转反馈（用户追问编码器角度影响）

用户：「改一下吧但是他反转的话不会影响编码器的计算的角度吗」

### 核心结论：取反位置决定成败
反装电机的正确做法是**在算 diff 之前就镜像 ecd**，不是最后把角度取负：

```c
const uint16_t ecd_raw = (data[0] << 8) | data[1];
uint16_t ecd = ecd_raw;
if (motor->reversed) {
  ecd = (C620_ECD_COUNT - ecd_raw) & (C620_ECD_COUNT - 1U);  /* 8192=2^13 */
}
receive_measure->last_ecd = receive_measure->ecd;  /* 也是镜像值 */
receive_measure->ecd = ecd;
/* 之后 diff / total_round / angle 全部自洽 */
```

### 三种做法的对错（仔细验算过，别记错）
| 做法 | 角度连续 | 内部自洽 |
|---|---|---|
| 先镜像 ecd（含 last_ecd）再算 diff | ✓ | ✓ 正确 |
| 只镜像 ecd，last_ecd 存原始值 | ✗ 每跨 0/8191 误判跨圈，跳 360° | ✗ |
| 最后把 total_angle_deg 取负 | ✓ | ✗ total_round 说 +1 圈、角度说 -360° |

**注意**：「最后取负」不会跳变（数学上 -total 仍连续），但 total_round 和
total_angle_deg 符号相反，谁拿 total_round 估速度就反了。我一开始误判成会跳，已修正注释。
